# INSTALL.md — Installing on a fresh machine (Windows / Linux)

English | [繁體中文](INSTALL.zh-TW.md)

This document assumes you already have: a machine with an **NVIDIA GPU**, **Hermes installed and running**,
and (optional, but this pack was designed around it) a **resident local LLM** managed by the **TRUSTA-AST backend**
(default `http://127.0.0.1:8571`). This pack never touches the inference engine directly; it only asks that backend's API for status.

The one-line install:

```
# Windows
.\install.ps1

# Linux
./install.sh
```

The rest of this document explains **why**, and where to look when something goes wrong.

---

## 0. Which directories this touches

First, where this writes. **Only three places**, and only one file needs editing by hand.

| Purpose | Windows | Linux | Created by |
|---|---|---|---|
| **Hermes home** | `%LOCALAPPDATA%\hermes` | `~/.hermes` | Hermes itself (already exists) |
| **Skills** (skills Hermes can read) | `%LOCALAPPDATA%\hermes\skills\{imggen,vidgen}\` | `~/.hermes/skills/{imggen,vidgen}/` | Copied in by `install` |
| **Engine** (planner, runner, workflows) | `%LOCALAPPDATA%\hermes\comfy-engine\` | `~/.hermes/comfy-engine/` | Copied in by `install` |
| **Config file** (★ the only thing you edit) | `…\comfy-engine\hermes-comfy.conf` | `…/comfy-engine/hermes-comfy.conf` | Generated by `install` |
| **ComfyUI itself + models** | Wherever you installed it | Wherever you installed it | You |
| **Hermes config** | `%LOCALAPPDATA%\hermes\config.yaml` | `~/.hermes/config.yaml` | Change one line: `terminal.timeout` |

A few things worth knowing:

- **Hermes decides where Hermes home is**, and it differs per platform (first row above).
  The installer uses exactly the same rules as Hermes, including the `HERMES_HOME` environment variable override.
  If you use a Hermes profile, add `--hermes-home <path>`.
- **The original reference machine kept the engine in `~/.hermes/comfy-launcher`**. On Windows that was just a folder that happened to share the name,
  but **on Linux `~/.hermes` is Hermes home itself** — the engine would sit directly in Hermes's home directory,
  easy to confuse with Hermes's own files. So this pack uses `<hermes home>/comfy-engine` instead, which means the same thing on both platforms.
- **No absolute paths are hard-coded in the code any more.** Everything is resolved by `engine/paths.py`,
  in the order "environment variable → `hermes-comfy.conf` → per-platform default".

## 1. Prerequisites

### Both platforms

| Item | Notes |
|---|---|
| GPU + driver | **Vendor-neutral**. The planner only asks "how much is in use, how much is left". **Vendor tools first, service APIs only if none answer**, in order: `VIDGEN_GPU_QUERY_CMD` → `nvidia-smi` → `intel-ze` (Intel Level Zero) → `xpu-smi` (Intel CLI) → `rocm-smi` (AMD) → ComfyUI's `/system_stats` → TRUSTA-AST's `/system/resources`. It reports FAIL only if all seven fail |
| TRUSTA-AST backend | Optional. If present, the planner knows "is the model loaded, which engine, how much VRAM it uses"; if unreachable, it **assumes the LLM is there** and reserves VRAM as usual (the conservative direction). Address via `VIDGEN_AST_URL` |
| Python 3.9+ | Runs the skills and the engine. ComfyUI's own python is a separate one, see below |
| ComfyUI | Must be recent enough to have the MiniMax-H3 core nodes (reference machine: **0.31.1**) |
| `ComfyUI-GGUF` custom node | The default video path (Wan 14B GGUF) and qwen/flux image generation both depend on it |
| Disk | At least 40 GB for models, 155 GB for everything. See `MODELS.md` |
| `ffmpeg` + `ffprobe` | **Required by `dramagen`** (the other two skills don't need them). It stitches each shot's clip into `final.mp4` and muxes in the subtitle track. Must be on PATH; `doctor.py` checks for it |
| An OpenAI-compatible LLM endpoint | **Required by `dramagen`**. `story.py` calls `/v1/chat/completions` to turn the story premise into `drama.json`. Defaults to `VIDGEN_AST_URL` (+`/v1`); set `DRAMAGEN_LLM_URL` to point elsewhere |

**12 GB or more** of VRAM is recommended. The reference machine is an RTX 5080 Laptop 16 GB; after the resident LLM's 7 GB,
about 7.5 GB is left for video. On a smaller card, lower `VIDGEN_LLM_VRAM_BUDGET`, or every run will be refused
(going below 7.0 also requires `VIDGEN_UNSAFE_OVERRIDE=1`, see below).

### Windows

- The **portable build** of ComfyUI (`ComfyUI_windows_portable`) is recommended;
  it ships its own `python_embeded\python.exe`, which is the one that has torch and PyAV.
- No separate CUDA toolkit is needed.

### Linux

- ComfyUI is usually a `git clone` + venv:

  ```bash
  git clone https://github.com/comfyanonymous/ComfyUI /opt/ComfyUI
  cd /opt/ComfyUI
  python3 -m venv venv
  ./venv/bin/pip install -r requirements.txt
  ./venv/bin/pip install av        # H3 audio muxing needs PyAV; requirements may not include it
  ```

  The installer automatically looks for `<COMFY_HOME>/venv/bin/python` or `.venv`.
- **Be sure to install `av` (PyAV)**: `vidgen r2v` produces "video + native stereo audio",
  and `h3_media.py` uses it to mux the two into an mp4. Without it, H3 fails at the last step.

## 2. Installation

### Windows

```powershell
cd <extracted hermes-comfy-pack>
.\install.ps1
```

If execution policy blocks it:

```powershell
powershell -ExecutionPolicy Bypass -File .\install.ps1
```

If ComfyUI is not in the default location, say so explicitly:

```powershell
.\install.ps1 --comfy-home D:/AI/ComfyUI_windows_portable
```

### Linux

```bash
cd <extracted hermes-comfy-pack>
chmod +x install.sh
./install.sh --comfy-home /opt/ComfyUI
```

### Following a git checkout: `--link`

On a machine that tracks this pack with git (a development box, or a product checkout
that updates itself with `git pull`), install it linked instead of copied:

```
python install.py --link
```

The engine and the skill scripts then run straight from the checkout; nothing is copied
and nothing is written into it. Only what differs per machine goes into the Hermes home:
`SKILL.md` rendered with this machine's paths, `hermes-comfy.conf`, and the runtime state
under `<hermes home>/comfy-state/` (jobs, logs, outputs). Updating is `git pull` and nothing
else: the installer adds `post-merge`, `post-checkout` and `post-rewrite` hooks (appended to
any hook already there) that re-render the documents, and each skill also checks on start
and refreshes them if the checkout changed without the hooks (`install.py --refresh` does
the same by hand). A machine that had a copy install keeps its settings: the old conf
seeds the new one, and the old skill folders are moved to `comfy-state/skill-backups/`.

### Preview what it will do

```
python install.py --dry-run
```

### What the installer actually does

1. Copies `engine/` → `<hermes home>/comfy-engine/` (the engine's programs + 12 workflows)
2. Generates `hermes-comfy.conf` with the detected `COMFY_HOME` filled in
3. Copies `skills/` → `<hermes home>/skills/`, and **rewrites the absolute paths in SKILL.md to this machine's actual paths**
4. Writes an `engine_dir.txt` into each skill directory so the skill can find the engine at run time
5. Builds `<hermes home>/motion-venv`, a Python environment of its own for the `motion` skill (OCR and
   barcode packages from `skills/motion/requirements.txt`; Hermes's own venv is never touched), rebuilt only
   when that file changes. Built with uv when there is one (`UV`, then `<hermes home>/bin/uv`, then PATH),
   which needs no pip in either interpreter; with pip otherwise
6. Copies the pack's ComfyUI node into `custom_nodes/` and runs `tools/doctor.py`

Step 3 is the key one: SKILL.md tells the model to run **a single command with full absolute paths**,
so those paths have to be real. The source file is `SKILL.md.in`, containing placeholders such as `@@PY@@` and `@@VIDGEN@@`.

Re-running the installer is safe: existing files are first backed up as `<name>.bak.<timestamp>`,
and `hermes-comfy.conf` is left untouched (delete it first if you want it regenerated).

## 3. Settings to change

### ★ `hermes-comfy.conf` (in `<hermes home>/comfy-engine/`)

The installer fills in most of it. In practice only two values need checking:

```ini
# 1. Where ComfyUI is. Both layouts are detected automatically:
#    Windows portable: <COMFY_HOME>/ComfyUI/main.py + <COMFY_HOME>/python_embeded/
#    Linux git clone : <COMFY_HOME>/main.py         + <COMFY_HOME>/venv/
COMFY_HOME=/opt/ComfyUI

# 2. ★ Always reset this on a new machine: VRAM used by the resident LLM.
#    This is an unconditional reservation, even when the LLM is not loaded at the moment —
#    otherwise memory gets used up while it is away, and it gets crushed when it comes back.
#    This value can only be raised: settings below the default 7.0 are ignored (a refused
#    job must not be able to lower its own guard), with a notice on stderr when ignored. So
#    "no resident LLM, use the whole card" requires setting both:
#        VIDGEN_UNSAFE_OVERRIDE=1
#        VIDGEN_LLM_VRAM_BUDGET=0
VIDGEN_LLM_VRAM_BUDGET=7.0
```

Everything else (`COMFY_PYTHON`, `HERMES_COMFY_ENGINE`, the various memory margins) has working defaults;
if `doctor.py` says they are fine, leave them alone. Full documentation is in the comments of `hermes-comfy.conf.example`.

### Hermes `config.yaml`

```yaml
terminal:
  timeout: 600
```

Video renders routinely take several minutes. Too short a default kills the foreground command mid-render —
**the render itself does not fail** (the worker is detached, finishes on its own and writes the mp4),
but you won't get the foreground result and have to reattach with `gen.py status <job_id>`.
`doctor.py` checks this setting.

### How to start the resident LLM (if you have one)

**Have the inference engine under AST load weights with mmap** (the default for most GGUF loaders).
That way the weights are clean, file-backed pages that the OS can drop for free at any time and read back from the SSD,
and the planner counts them as "available memory", so it can admit more work.
If the weights are dirty private pages (mmap disabled, or the engine reads the file instead of mapping it), dropping them requires writing to swap/pagefile,
and the planner automatically counts them as 0 (this is **measured**, not something you configure), so the videos you can generate get shorter.

> **⚠️ The inference engine may tell you to do the opposite. Don't follow it.** When loading with MoE CPU offload
> (`-ncmoe` / `--n-cpu-moe`), some engines print a warning like this:
>
> ```
> W tensor overrides to CPU are used with mmap enabled
>   - consider using --no-mmap for better performance
> ```
>
> It is right — **for the LLM's own load and inference speed**. But on this machine the LLM is not the only user:
> with mmap off, those weights become dirty pages that can't be reclaimed for free, the planner's reclaimable amount drops to 0,
> and the maximum video length shrinks with it. **The optimum for each side is the opposite of the other; you have to pick one.**
>
> Measured (5060 Ti 16GB / 128GB RAM, 30B-A3B loaded with `-ncmoe 39`): with mmap kept on,
> reclaimable pages **9.8 GB**, RAM budget **94.9 GB**; with mmap off, **0 GB** and **80.6 GB**.
>
> This pack defaults to the video side. If this machine is mainly for LLM inference and video is only occasional,
> do the reverse and turn mmap off, knowing that videos will be shorter.

> Older versions had a `VIDGEN_LLM_MLOCK` flag asking you to "declare" whether the weights were locked in RAM. **It has been removed.**
> It was a declaration, not a measurement: a wrong declaration loosened exactly the margin that protects the agent, and for most
> engines the default was wrong. Linux now measures it directly from `VmLck`, so locked pages naturally count as 0.

## 5. Getting started

After installing, **restart Hermes** so it picks up the new skills. Then just use natural language:

- "Generate a Shiba Inu wearing a space helmet, flat vector illustration" → goes to `imggen`
- "Make this image move" → goes to `vidgen i2v`
- "Make a video with sound starring this person" → goes to `vidgen r2v` (MiniMax-H3)

The two SKILL.md files contain full model-selection guidance and known pitfalls; Hermes reads them itself.
A few of these were learned the hard way through testing; don't work around them:

- **Don't use `t2v` without a starting image** — the 14B model in this setup is an I2V model; text alone produces **pure noise**,
  and still returns `ok:true` with an mp4 path. Always go two-stage: "`imggen` a still first → then `i2v`".
  `gen.py` already blocks `t2v` outright.
- **Don't send another prompt while rendering** — see the next section.

## 6. Memory handover: the core of this design, and where the platforms differ

What makes this pack unusual is that it assumes **an LLM you are actively using also lives on the same machine**, and
**the agent driving this whole pipeline is that LLM**.

The sequence is fixed:

```
start protected ComfyUI → submit prompt → confirm it really appears in queue_running
                                          → only then hand over the DRAM the LLM holds
```

The order cannot be reversed. If memory is released before ComfyUI has actually started rendering, and startup then fails or the job is refused,
the memory is given up for nothing, not a single frame of video is produced, and the agent already has to re-read its own weights from SSD — which looks like all of Hermes freezing.
`memplan.release_llm_dram()` is the only place that performs a release, and it **checks `/queue` itself** rather than trusting the caller.

**What the release does**: it reclaims the LLM process's **clean, file-backed mmap weight pages**.
The process keeps running, VRAM is untouched, the model is not unloaded; the next inference just re-reads from SSD.

**Which process gets reclaimed is decided entirely by AST, and confirmed by the operating system.** The approach deliberately contains no names;
three paths are tried in order:

1. **Walk the process tree** (primary path). `VIDGEN_AST_URL` reveals one thing: which port the backend is on.
   Ask the OS who is listening on that port — that is AST itself; then walk its descendants **recursively**,
   which are the things it launched. Recursion is not optional: if the backend spawns the engine through a worker,
   the engine sits at the **second level**, and looking only at direct children stops at the worker and misses exactly the process holding the weights.
   Parent-child relationships are also checked against **creation time** — Windows does not clear the dead parent pid of an orphaned process,
   and that pid may already have been reused by something else; comparing ages filters out such false descendants.
2. **Use ports to corroborate, not to find**. Every port-like number in AST's payload is checked
   against "who is listening", but **it is trusted only if that process is also a descendant of AST**, and it is used only
   for ordering and labelling, never for inclusion or exclusion. Ports alone are too loose — `n_ctx: 64000` and `n_batch: 512`
   are integers too, and pruning based on them would hit unrelated services.
3. **Absolute paths in the payload** (fallback). Take the file name as a candidate and ask the process table who is running it
   (data files such as model weights are excluded; descriptive text containing slashes is excluded too, since it is not an absolute path).
   This path is kept because when the backend is not local, or not on the same OS (e.g. a WSL split install), there is no process tree
   to walk, but the binary name it reports can still be matched on this side.

Every process found is trimmed. When the backend spawns the engine itself, the worker and the engine each hold part of the DRAM;
trimming only the largest one would leave the rest in place.

So this pack **does not know and does not need to know**: which field AST reports in, what that field is called, or which
inference engine runs underneath. If AST swaps engines or renames fields, nothing here has to change.

The reasoning is that this pack is paired with AST, and the engine under AST is swappable, so every hard-coded
name this pack ever tried was right on the machine it was written on and wrong on the next — and they all failed silently in the same way:
`find_pid()` found nothing and the handover did nothing. Which engine is running is not a question this pack is entitled to answer.

A model running inside AST's own worker (no separate engine process) **is covered too**: the walk then stops at the
worker, and the worker is the correct target. This is exactly the case where the old approach got no candidates and silently did nothing.

The only true "nothing to reclaim" case left is when nobody is listening on that port, i.e. the backend is not a process
on this machine at all. DRAM reclaim is then disabled and the planner counts the reclaimable amount as 0 (the conservative direction: slightly shorter
videos rather than squeezing out the agent), and `memplan` says so once on **stderr**.

`VIDGEN_LLM_PROCESS` is still the highest-priority override, for deployments AST does not manage. It **bypasses** the
"confirmed running" check above — if you name a process that isn't running, you should be told, not silently ignored.

> Incidentally: AST's `/inference/cleanup_generation_memory` is **not** a substitute for this;
> it clears the KV cache and intermediate activations, and `/inference/force_cleanup_gpu` even restarts the worker,
> which is exactly the eviction this pack exists to avoid. So reclaim still happens at the OS level; only the target is decided by the API.

| | Windows | Linux |
|---|---|---|
| Measuring "available RAM" | `GlobalMemoryStatusEx` | **MemAvailable** from `/proc/meminfo` |
| Measuring the LLM's reclaimable amount | `WorkingSetSize − PrivateUsage` (PSAPI) | `VmRSS − (RssAnon + VmLck)` (`/proc/PID/status`) |
| Actual reclaim | `EmptyWorkingSet` | `process_madvise(MADV_PAGEOUT)` |
| Consequence of reclaim failing | **Matters**: Windows does not proactively reclaim another process's clean pages for you, so the memory stays occupied | **Almost none**: Linux already drops clean file-backed pages under memory pressure |

**A Linux-specific point**: `process_madvise(MADV_PAGEOUT)` on "another process" requires
`CAP_SYS_NICE`, **and being its parent process does not count**; it has nothing to do with Yama's `ptrace_scope`.
(Measured: with `ptrace_scope=1`, calling it on a child process you spawned yourself still gives `EPERM`; after adding that capability,
the same process succeeds, 395 MB → 10 MB. See `tests/test_tree_live.py`.)
So being blocked for lack of permission is **normal, not a fault** — it just loses an optimization that
"does the work ahead of time"; the budget calculation remains correct and videos are still generated.

### What "free memory" mechanisms Linux actually has (measured results)

The numbers below were measured on WSL2 / kernel 6.18, against a process holding 512 MB of mmap'd file pages
(equivalent to an inference engine that loads a GGUF via mmap):

| Mechanism | Result | Requires | Notes |
|---|---|---|---|
| `process_madvise(MADV_PAGEOUT)` | ✅ **522 → 8 MB** | `CAP_SYS_NICE` or ptrace permission | This is what the engine uses built-in; **targets only the specific process** |
| Same, without permission | ❌ EPERM, no change | — | The default `ptrace_scope=1` blocks it |
| cgroup v2 `echo N > memory.reclaim` | ✅ **522 → 6 MB** | root + **the process must be born in that cgroup** | A whole-**cgroup** operation, not per-process |
| `/proc/sys/vm/drop_caches` | System-wide page cache | root | Too blunt; affects every program |
| `/proc/<pid>/clear_refs` | **Frees no memory at all** | — | Only resets the accessed bits; a common misconception |
| `/proc/<pid>/reclaim` | Does not exist | — | Only on Android / vendor kernels |

**Two pitfalls hit during testing, worth knowing up front:**

1. **"Moving" a process into a cgroup does not work.** cgroup v2 charges pages to "the first cgroup that read them in",
   so after moving it in, `memory.current` is 0 and every reclaim returns EIO, which looks like the feature is broken.
   The process has to be **started in that cgroup from the beginning** — services managed by systemd already are
   (`system.slice/<unit>`), so normal deployments are fine.
2. **If the amount requested from `memory.reclaim` exceeds the actually charged amount, it returns EIO even if it really did reclaim.**
   Judge success by the amount actually reclaimed (how much RSS dropped), not by the exit code.

### Ready-to-use helper

The pack ships **`tools/linux-reclaim-helper.sh`**, which tries both mechanisms in order; just plug it into the existing escape hatch:

```ini
# hermes-comfy.conf
VIDGEN_LLM_RECLAIM_CMD=/path/to/tools/linux-reclaim-helper.sh
```

The engine calls it with the pid appended. It **first confirms the cgroup contains only the target process** before taking the cgroup path —
otherwise reclaim would hit every program in the same cgroup, which is exactly what this whole design is meant to avoid
(measured: an unconfigured WSL distro puts everything in `/init.scope`; without this guard it would sweep away the entire session).

The simplest way to give it permission is a sudoers line:

```
your-user ALL=(root) NOPASSWD: /path/to/tools/linux-reclaim-helper.sh
```

Then set `VIDGEN_LLM_RECLAIM_CMD` to `sudo /path/to/tools/linux-reclaim-helper.sh`.

> **Worth repeating**: on Linux this is an **optimization, not a necessity**. Linux already drops clean file-backed pages
> under allocation pressure; without this helper the planner's budget calculation is still correct, it just loses the early release.
> Windows has no such behaviour, which is why it is mandatory there.

### Engines that fill the GPU: lent, not protected

Everything above assumes the LLM holds a fixed share of the card. Some engines size themselves to the
whole GPU on purpose — Strata (behind TRUSTA-AST) fills its expert cache until ~0.3 GB is left, 14.3 GB of
a 16 GB card. Holding that back for it would leave nothing to render with, so for these engines
— decided by measurement, not by engine name: any LLM behind AST that holds more VRAM than
`VIDGEN_LLM_VRAM_BUDGET` (7 GB by default) — every render **borrows** the GPU instead
(`engine/llmsleep.py`):

1. wait until the LLM is idle — the agent's last message ("rendering started, please wait") may still be streaming;
2. `POST /inference/sleep`: the engine copies its non-cache VRAM to page-locked host RAM and keeps the conversation;
3. if the sleep is refused — on Windows the backup must fit in free **commit** plus 2 GiB, and Strata's resident mode
   page-locks 13.5 GiB of experts at load, so on a 32 GB box it never fits — `POST /inference/unload_model`
   instead (AST saves the conversation to a slot file and restores it on the next load);
4. render; then wake it, or `POST /inference/load_model` with the same config (~35 s).

The planner counts that LLM's VRAM (read from the per-process GPU counters; AST reports 0 for Strata) and,
when it will be unloaded, its RAM as available, and `start_comfy.py` does not reserve it. A lent LLM is
recorded in `jobs/LLM_LENT.json`. `recast` keeps it lent for a whole run and returns it once at the end.

| Setting | Effect |
|---|---|
| `VIDGEN_LLM_SLEEP=off` | never lend; hold VRAM back as for any other engine |
| `VIDGEN_LLM_RETURN=defer` | keep it lent after this job (what `recast` sets for its passes) |
| `gen.py llm-return` (vidgen) | give a lent LLM back now — after an interrupted run |

While the GPU is lent, **the agent cannot answer anything**: it is asleep or unloaded until the render ends.

## 6.5 WSL split install (Hermes in Ubuntu, ComfyUI stays on Windows)

This is a special layout: **Hermes and this engine run in WSL's Ubuntu, while ComfyUI, the model files and the
resident LLM all stay on Windows.** The two sides communicate over two channels, and nothing is copied:

```
WSL Ubuntu                                   Windows
  Hermes + imggen/vidgen + engine    ──HTTP──▶  ComfyUI :8188
                                     ──/mnt/c─▶  models/, input/, output/
                                        ?         TRUSTA-AST + LLM (see limitations below)
```

### Installation

```bash
# Inside Ubuntu (copy or mount this pack in first)
cd /mnt/c/Users/<you>/comfyui-skill
./tools/wsl_bootstrap.sh --dry-run     # see what it detects first
./tools/wsl_bootstrap.sh
```

It detects the Windows home directory (asks Windows for `%USERPROFILE%` instead of guessing), finds ComfyUI,
probes reachable addresses, installs the apt packages and Hermes, installs PyAV into Hermes's venv, runs `install.py`,
and finally writes the split-layout settings into `hermes-comfy.conf`.

### Two network issues you must handle

**1. Enable WSL mirrored networking.** WSL2 defaults to NAT mode, where Ubuntu has its own network namespace,
so **Windows's `127.0.0.1` is not Ubuntu's `127.0.0.1`**. ComfyUI binds only to `127.0.0.1`,
so in NAT mode WSL cannot reach it. With mirrored networking both sides share loopback, and no ports need to be opened:

```ini
# %USERPROFILE%\.wslconfig
[wsl2]
networkingMode=mirrored
```

After changing it, run `wsl --shutdown` on Windows for the setting to take effect, then start ComfyUI on Windows:

```
python <windows-engine>\start_comfy.py
```

**Why ComfyUI must not be exposed to the network**: ComfyUI has no authentication at all. Once bound to `0.0.0.0`,
anyone on the same network can run jobs on your GPU and read every image and video it produced, and with ComfyUI-Manager installed
they can also install custom nodes, which amounts to running arbitrary code on your computer. So `start_comfy.py` does not offer
`--listen`, and `--listen` in `COMFY_EXTRA_ARGS` is rejected too. Hermes on other computers uses the chat model only through
AI Scaler Toolkit's `/v1` (with an API key); images and videos are generated on the computer where Hermes runs.

**2. Don't hard-code the host address.** With mirrored networking just use `127.0.0.1`. The engine's
`paths.comfy_url_candidates()` tries the configured value first; only in NAT mode does it add the current default gateway
(the Windows host, which may change on every WSL restart), and `_resolve_comfy_url()` picks the first one that responds and remembers it.
When ComfyUI binds only to `127.0.0.1`, the gateway route is unreachable, so in practice you rely on mirrored networking.

### ⚠️ Memory protection degrades across the OS boundary (must read)

The core value of this pack is protecting the resident LLM on the same machine. **With the LLM on Windows and the engine in Ubuntu,
only half the protection remains**, and it is a predictable half:

| Mechanism | Still effective after the split? | Why |
|---|---|---|
| **VRAM reservation** (`VIDGEN_LLM_VRAM_BUDGET`) | ✅ **Fully effective** | It is an unconditional reservation that doesn't need to see the LLM process; and WSL's `nvidia-smi` reads **the same physical card**, so usage on the Windows side is counted too |
| ComfyUI's `--reserve-vram` | ✅ Effective | Set by `start_comfy.py` on the Windows side, independent of WSL |
| **LLM DRAM reclaimable-amount calculation** | ❌ **Broken** | Ubuntu's `/proc` cannot see Windows processes, no PID is found → reclaimable amount counts as 0 |
| **LLM DRAM active reclaim** | ❌ Broken | `EmptyWorkingSet` cannot be called on a Windows process |

**The two broken items fail "conservative", not "dangerous"**: counting the reclaimable amount as 0 only makes the RAM budget smaller and refusals more likely;
it never makes it take memory from the LLM. The VRAM safeguard that actually matters is fully intact. `doctor.py` flags this as WARN and explains it.

**If you want to restore the DRAM side too**, `VIDGEN_LLM_RECLAIM_CMD` is the escape hatch reserved for exactly this:
point it at a small tool that calls PowerShell on the Windows side via WSL interop (the pid is appended to the command).

**One more number to know**: Ubuntu's `/proc/meminfo` reports **the memory allocated to the WSL virtual machine**
(by default half of the host), not Windows's physical RAM. The default GGUF path only adds about 1 GB of RAM,
so in practice this does not affect decisions, but **don't take the RAM figure doctor reports as Windows's available memory**.
To make the two consistent, set a limit with `memory=` in `.wslconfig`.

### Everything else is configuration, not code

The good news is that the split layout only requires configuration changes:

```ini
COMFY_REMOTE=1                        # Don't try to start ComfyUI here (auto-detection sets this too)
COMFY_URL=http://127.0.0.1:8188      # with mirrored networking, Windows' loopback is here
COMFY_ROOT=/mnt/c/Users/<you>/ComfyUI_windows_portable/ComfyUI
COMFY_PYTHON=/home/<you>/.hermes/hermes-agent/venv/bin/python
VIDGEN_AST_URL=http://127.0.0.1:8571  # the backend is on Windows too, also over loopback
```

Pointing `COMFY_PYTHON` at **Ubuntu's own** python is deliberate: it is only used to run `h3_media.py`,
which needs only **PyAV + Pillow, not torch**. Pointing it at Windows's `python_embeded\python.exe`
would actually break (Linux paths fed to a Windows executable). `paths.py` now refuses to pick an `.exe` on non-Windows systems.

Input images are staged by **copying them into `COMFY_INPUT`**, so `/mnt/c/.../ComfyUI/input` is enough,
with no file-sharing setup needed.

### Hermes's LLM endpoint

With mirrored networking on, `127.0.0.1` in WSL is Windows, so Hermes points straight at
the AI Scaler Toolkit backend on this machine:

```
hermes setup      # base_url: http://127.0.0.1:8571/v1
```

To the backend that is a **local** connection: **no API key, and no need to turn on
AI Scaler Toolkit's "Let another computer use this machine's model"**. The backend serves
the OpenAI-compatible `/v1` itself, so point at it -- **never around it at the inference
engine's private port**: that port listens on `127.0.0.1` only and takes an internal key
only the backend knows, so a direct connection is refused. Through the backend you get the
same API, and nothing changes on your side when the model or the engine does.

In the config file (`~/.hermes/config.yaml`) you add an entry to `custom_providers` and
point `model.provider` at it. **The easiest and least error-prone way is to copy the
Windows `config.yaml` over** -- under mirrored networking `base_url` stays as it is.
`model.provider` is a slug derived from `custom_providers[].name`
(`custom:local-(127.0.0.1:8571)`), so a hand-added entry easily ends up with a slug that
does not match, and an unknown provider.

**If mirrored networking is not an option**: AI Scaler Toolkit can let another computer
in -- Settings → Network, "Let another computer use this machine's model" -- and you reach
`/v1` at the Windows address with the API key shown there (the provider's `api_key`). But
ComfyUI listens on `127.0.0.1` only, so a NAT-mode distro still cannot reach it: image and
video generation need mirrored networking either way.

**Verify (inside Ubuntu)**:

```bash
curl -s http://127.0.0.1:8571/health          # -> {"status":"healthy",...}
curl -s http://127.0.0.1:8571/v1/models       # -> the model that is loaded
curl -s http://127.0.0.1:8188/system_stats    # -> answers only while ComfyUI is running
```

> **Note on hybrid reasoning models**: models such as Qwen3.5 put their thinking in
> `reasoning_content`. Testing with a small `max_tokens` (say 16) lets the thinking tokens
> use it all up, and `content` comes back empty, which looks broken. Use 256 or more.

## 7. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `doctor.py` says `main.py` not found | `COMFY_HOME` points to the wrong place. It must point to the level that **contains** ComfyUI: for portable, the folder containing `ComfyUI\` and `python_embeded\`; on Linux, the cloned ComfyUI itself |
| `ComfyUI's python not found` | Set `COMFY_PYTHON`. It is **not** the one that runs the skills; it is the one with torch + PyAV |
| `custom node ComfyUI-GGUF` FAIL | See the last section of `MODELS.md`; git clone it into `custom_nodes/` |
| `no GPU measurement source answered` | All seven sources failed. Install the vendor tool (`nvidia-smi` is usually in `/usr/bin` on Linux, `C:\Windows\System32` on Windows), or start ComfyUI / the AST backend first so their APIs can answer, or set `VIDGEN_GPU_QUERY_CMD` |
| H3 video fails at the last step | ComfyUI's python is missing PyAV: `<COMFY_PYTHON> -m pip install av` |
| `Python was not found` on Windows | You hit the Microsoft Store stub. This is exactly why the commands in SKILL.md **use an absolute path even for the interpreter**; copy them as-is, don't change them |
| Paths become `C:Users<you>…` on Windows | Hermes's terminal is bash and the backslashes got eaten. Use forward slashes (Windows Python accepts them) |
| Every run is refused for insufficient VRAM | `VIDGEN_LLM_VRAM_BUDGET` is too large for your card. Set it to the LLM's actual usage; going below 7.0 (including 0 for no LLM) also needs `VIDGEN_UNSAFE_OVERRIDE=1`, otherwise it is ignored with a notice on stderr |
| The command timed out | **Don't resubmit.** Rendering runs in a separate detached worker and finishes on its own. Reattach with `gen.py status <job_id>` (`--wait` prints the job_id to stderr right at the start) |
| Every message fails while a video renders (a local LLM that fills the GPU) | Expected: the LLM lent its GPU to the render and comes back when it ends (~35 s). If a render was interrupted and the model stays unloaded, run vidgen's `gen.py llm-return` |
| Hermes doesn't see the new skills | Restart Hermes |
| Hermes's curator modified my skills | Use `install.py --external` instead, which registers this pack's `skills/` directory in `skills.external_dirs` in `config.yaml`. Skills in external directories are protected and the curator won't rewrite them |

## 8. Moving over from this reference machine

The engine and skills are covered by this pack. You only need to bring two extra things:

1. **Models** (154.5 GB, or just the part you need) — see `MODELS.md`
2. The **`ComfyUI-GGUF`** custom node

**Not needed**: `jobs/`, `out/`, `logs/` (runtime artifacts, recreated automatically).

After moving, reset `VIDGEN_LLM_VRAM_BUDGET` for the new machine's GPU.
The "longest single segment per resolution" table in the `vidgen` SKILL.md was measured on a 16 GB card, **so treat it only as an order-of-magnitude reference** —
go by the live report from `gen.py plan`; the engine already blocks on its own based on current headroom.
