Trusta AST Fine-tune Service Manual

This document explains the architecture, API workflow, dataset formats, and complete operating procedures of the fine-tuning service. It is intended for team training.

Supported methods: LoRA / QLoRA / Full Parameter Fine-tuning. Trained models are automatically converted to GGUF Q4_K_M format.

A Traditional Chinese version of this manual is available: finetune_manual.html.

1. Architecture Overview

The Fine-tune Service uses the same multi-process isolation architecture as the Inference Service. Training runs in a dedicated worker process, so an OOM or a crash never affects the main FastAPI service.

Progress does not come back over the status queue alone. Every stage, metric, resource sample and error is written by JobLogWriter to events.jsonl (the durable record) and to Redis, and is served over /training/{job_id}/log and its SSE stream. See docs/training-log-frontend-integration.md.
Important: The worker process always exits when training ends, whatever the outcome (completed / stopped / error), guaranteeing that VRAM is fully released. The next training run starts a fresh worker.

2. Training Methods Compared

LoRA

Low-Rank Adaptation

  • Trains only low-rank matrices, very few parameters
  • Low GPU requirements
  • Fast training
  • Output: adapter weight files

QLoRA

Quantized LoRA (4-bit)

  • Base model loaded with 4-bit quantization
  • Even lower GPU requirements (fits consumer GPUs)
  • Slight loss of precision
  • Output: adapter weight files

Full Parameter

Full-parameter fine-tuning

  • Trains every parameter
  • Requires a large amount of GPU VRAM
  • Best quality
  • Usually paired with DeepSpeed ZeRO

3. Key APIs and Workflow

All training APIs are prefixed with /training/ and defined in service/app.py.

1. Start training

POST /training/start

Behavior: synchronous validation, asynchronous training.

Send a complete TrainingConfig. Once validation passes, the endpoint returns a session_id immediately; the actual training runs in the background worker process.

Note: a non-empty output_dir is rejected, but asynchronously. POST /training/start returns 200 with a session_id regardless; the worker performs the check and the failure surfaces via /training/status and the job log.

2. Query training status

GET /training/status

Behavior: synchronous, intended for polling.

Returns a TrainingStatus containing is_training, progress (0–1), current_step, total_steps, loss, current_epoch, status, and error.

3. Stop training

POST /training/stop

Behavior: force-terminates the worker process (terminate + kill).

It does not wait for a graceful shutdown; the process is killed and the state is reset. Checkpoints already written are unaffected.

4. Training history

GET /training/status/{session_id}/history

Returns the detailed loss / learning_rate / epoch records for that training session.

Records are stored in Redis (when available) or in memory, indexed by session_id.

5. System resource history

GET /system/resource/{session_id}/history

Returns the CPU / GPU / disk usage history recorded during training. Resource sampling is a background timer, not step-driven: it runs every TRAINING_MEM_SAMPLE_INTERVAL seconds (default 5.0) and starts before the model is loaded. Only trainer metrics (loss / lr / epoch) follow logging_steps.

6. Error details

GET /training/error_details

Retrieves the full training error traceback, including the is_oom flag. The format matches /inference/error_details.

7. Force GPU cleanup

POST /training/force_cleanup_gpu

Force-terminates the training worker process and resets the state. Use it when VRAM is still held after an OOM (the inference worker is unaffected).

End-to-end training example (Python)

import requests, time

BASE = "http://localhost:5000"

# Step 1: start training
config = {
    "model_name": "Qwen/Qwen3-4B",
    "method": "lora",
    "dataset_path": "dataset/mydataset.jsonl",
    "output_dir": "./output/qwen3_lora_v1",
    "lora_r": 16,
    "lora_alpha": 32,
    "lora_dropout": 0.05,
    "num_train_epochs": 3,
    "per_device_train_batch_size": 1,
    "gradient_accumulation_steps": 8,
    "learning_rate": 2e-4,
    "max_seq_length": 2048,
    "prompt_field": "prompt",
    "completion_field": "completion",
    "use_sft_trainer": True
}

resp = requests.post(f"{BASE}/training/start", json=config)
session_id = resp.json()["result"]["session_id"]
print(f"Training started: session_id={session_id}")

# Step 2: poll for progress
while True:
    status = requests.get(f"{BASE}/training/status").json()
    if status["is_training"]:
        print(f"  Step {status['current_step']}/{status['total_steps']} "
              f"| Progress: {status['progress']:.1%} "
              f"| Loss: {status.get('loss', 'N/A'):.4f}"
              f"| Epoch: {status.get('current_epoch', 0):.2f}")
        time.sleep(10)
    else:
        print(f"Training ended: status={status['status']}")
        if status.get("error"):
            print(f"Error: {status['error']}")
        break

# Step 3: fetch the detailed loss curve
history = requests.get(f"{BASE}/training/status/{session_id}/history").json()
for log in history["logs"]:
    print(f"Step {log['step']}: loss={log['loss']:.4f}, lr={log.get('learning_rate')}")

4. Code Structure

File path Role and responsibilities
service/app.py API entry point. Defines the /training/* routes and calls into training_manager.
service/training_manager.py Singleton facade. Exposes start_training, get_status, stop_training, get_history, and related methods to the API layer, with concurrency protection via a Lock.
service/training/training_process.py Process control core. Contains:
  • TrainingProcessManager: manages the worker process lifecycle, the IPC queue, status parsing, and reading history from Redis.
  • _training_worker_process(): the main loop that actually runs in the child process and handles start/stop commands.
service/training/core/strategies.py Strategy pattern.
  • StrategyFactory: picks a strategy based on use_sft_trainer.
  • SFTStrategy: uses the TRL SFTTrainer (recommended; supports completion-only loss).
  • CausalLMStrategy: uses the native HF Trainer (manual tokenization).
service/training/sft_runner.py SFTTrainer initialization. Builds CustomSFTTrainer (which overrides save_model for DeepSpeed + LoRA compatibility) and SFTConfig.
service/training/core/model_loader.py Model and tokenizer loading. Applies the appropriate BitsAndBytesConfig and LoraConfig for the chosen method (LoRA / QLoRA / full).
service/training/core/dataset_loader.py Dataset loading. Reads JSONL data and converts it into a HuggingFace Dataset object.
service/training/core/model_saver.py Result saving. Saves model weights and the tokenizer, then calls model_registry to register the fine-tuned model under the finetuned type.
service/utils/conversion_manager.py GGUF conversion. After training, automatically invokes the llama.cpp conversion scripts to produce a Q4_K_M quantized GGUF file.
service/configs/deepspeed/ DeepSpeed configuration templates. Five preset ZeRO-3 offload combinations:
  • zero3_offload_cpu_cpu.json: both optimizer and params offloaded to CPU
  • zero3_offload_cpu_cpu_tight.json: same devices, trimmed settings for constrained hosts
  • zero3_offload_cpu_disk.json: optimizer→CPU, params→disk
  • zero3_offload_disk_cpu.json: optimizer→disk, params→CPU
  • zero3_offload_disk_disk.json: both offloaded to disk (NVMe)

5. Training Process in Detail (Deep Dive)

Worker process main flow

1
Receive the start command
The worker pulls {"command": "start", "config": {...}, "session_id": "..."} from the request queue. It then checks whether output_dir already contains files (if so, it reports an error to prevent overwriting).
2
Strategy selection
StrategyFactory.get_strategy(config):
  • use_sft_trainer=True (default) → SFTStrategy (uses the TRL SFTTrainer)
  • use_sft_trainer=False → CausalLMStrategy (uses the native HF Trainer with manual tokenization)
At the same time, TrainingArguments is initialized (including the DeepSpeed config, BF16, and gradient checkpointing).
3
Load resources (done in order, to conserve memory)
  1. Load the tokenizer (AutoTokenizer.from_pretrained).
  2. Load the dataset (JSONL → HuggingFace Dataset).
  3. With CausalLMStrategy, pre-tokenize the dataset at this point (avoids CPU stalls during training).
  4. Load the model (applying the quantization settings and PEFT LoraConfig for the chosen method).
4
Prepare the trainer
strategy.prepare_trainer(model, tokenizer, dataset, training_args).
  • SFTStrategy: builds CustomSFTTrainer, which handles prompt+completion loss masking automatically (completion_only_loss=True).
  • CausalLMStrategy: builds CustomTrainer using default_data_collator. DataCollatorForLanguageModeling was deliberately removed — it overwrote the prompt masking.
A _ProgressCallback is attached that reports progress to the status queue and writes it to Redis every logging_steps.
5
Run training
trainer.train(). Every logging_steps during the run it:
  • pushes {"status": "progress", "step": N, "loss": ..., "epoch": ...} to the status queue;
  • samples CPU / GPU / disk usage and stores it in Redis.
6
Save results
save_training_results(trainer, tokenizer, training_config) writes the adapter or the full model to output_dir and automatically calls model_registry to register it as a finetuned model.
7
Clean up resources and convert to GGUF
_cleanup_training_resources() runs first (deleting the trainer / model / tokenizer objects, running GC, and emptying the CUDA cache). Once VRAM is released, _convert_training_output_to_q4_k_m() is called to perform the GGUF conversion.
8
Report completion and exit
Pushes {"status": "completed", "gguf_path": "...", "gguf_quantization": "Q4_K_M"} to the status queue. The worker process then exits, guaranteeing that all resources are released.

Progress state machine

stateDiagram-v2 [*] --> idle idle --> starting: start_training() starting --> initializing: Worker receives command initializing --> running: trainer.train() begins running --> completed: Training succeeded + GGUF conversion running --> stopped: stop command received running --> error: OOM or exception completed --> idle: Next training run stopped --> idle: Next training run error --> idle: After force_cleanup_gpu

6. Dataset Format

dataset_path accepts two things: a local .jsonl (one JSON object per line) or .json file, or — for any other value — a Hugging Face Hub dataset id. See Loading a dataset from the Hugging Face Hub below for the Hub case, which behaves differently in one important way.

For a local file, the loader sniffs the format from the literal column names text, prompt+completion and messages, plus an optional images/image field for multimodal training — four modes in total. prompt_field / completion_field / text_field rename columns after loading, so the file itself must still use the literal names above.

Mode 1: single text field (loss over the full sequence)

Use for: language-model pre-training, or any case where the entire sequence should be trained on. Set text_field: "text" (or the matching field name).

// dataset.jsonl (one record per line)
{"text": "### Question:\nHow do I set the Linux system timezone?\n\n### Answer:\nUse the timedatectl command: sudo timedatectl set-timezone Asia/Taipei"}
{"text": "### Question:\nWhat is a Docker volume?\n\n### Answer:\nA Docker volume is the mechanism used to persist container data..."}
{"text": "This is a passage of text for the model to learn from..."}

Mode 2: prompt + completion fields (completion-only loss)

Use for: instruction fine-tuning. SFTTrainer automatically masks the loss on the prompt and computes loss only over the completion.

Set prompt_field: "prompt" and completion_field: "completion".

// mydataset.jsonl (one record per line)
{"prompt": "You are a Linux system administrator.\nHow do I check system memory usage?", "completion": "Use the free -h command to check memory usage:\n```\nfree -h\n```\nThe -h flag displays the values in human-readable form..."}
{"prompt": "Explain what the GIL is in Python", "completion": "The GIL (Global Interpreter Lock) is a mechanism in CPython..."}
{"prompt": "How do I undo the last commit in Git?", "completion": "There are a few ways:\n1. Keep the changes: git reset --soft HEAD~1\n2. Discard the changes: git reset --hard HEAD~1"}
Recommendation: for instruction fine-tuning, use the two-field mode together with use_sft_trainer: true. The system then enables completion_only_loss=True automatically, so the model learns only the answer portion, which trains more efficiently.

Loading a dataset from the Hugging Face Hub

dataset_path is treated as a Hub dataset id whenever it does not end in .json or .jsonl. No extra flag is needed — just put the repo id where a file path would go: 

{
  "model_name": "Qwen/Qwen3-4B",
  "method": "lora",
  "dataset_path": "tatsu-lab/alpaca",     // Hub dataset id instead of a local path
  "prompt_field": "instruction",           // point the *_field options at the Hub dataset's own columns
  "completion_field": "output",
  "output_dir": "./output/alpaca_lora"
}

Split selection

The dataset is loaded without a split argument. If the result has splits, the train split is used; if there is no train, the first available split is used and a warning is logged naming the splits it saw. An empty split, or a dataset with no splits at all, raises an error.

Two limitations to be aware of.
  • No config / subset or split selector. The id is passed through as-is, so datasets that require a configuration name (e.g. wikitext with wikitext-2-raw-v1) or a specific split cannot be selected. Download such a dataset and save it as a local .jsonl instead.
  • Format auto-detection does not run for Hub datasets. The text / prompt+completion / messages sniffing described above only applies to local .json / .jsonl files. A Hub dataset is handed on as-is, and the mode is decided from its actual column names:
    • a messages column (or whatever messages_field names) → chat mode
    • both prompt_field and completion_field set → prompt+completion mode, with those columns renamed for TRL
    • otherwise → single-text mode, reading text_field (default text)
    So for Mode 2 with a Hub dataset you must set both prompt_field and completion_field explicitly; leaving them empty silently falls through to text mode and fails on a missing text column.

What does carry over to Hub datasets:

  • Held-out evaluation. eval_split_ratio is applied after loading, so it works the same way.
  • Multimodal. An images or image column is detected from the dataset's columns, so image training works provided a processor was loaded (enable_image_training).
  • Private and gated datasets. No token is passed explicitly, so this relies on ambient authentication — set HF_TOKEN (or HF_HUB_TOKEN) in .env, or sign in once with hf auth login.

Dataset quality guidelines

GuidelineDetails
Minimum dataset size At least 500–1000 records is recommended; quality matters more than quantity
Sequence length Keep within max_seq_length — anything longer is truncated. Aim for 95% of records to fit within the configured length
Data cleaning Remove duplicates, verify UTF-8 encoding, and avoid empty prompt/completion values
Format consistency Keep the prompt format consistent across the dataset (e.g. whether a system prompt is included)

7. Configuration and Parameters

Full TrainingConfig reference

{
  // === Required ===
  "model_name": "Qwen/Qwen3-4B",        // Model Registry label, or an HF model ID
  "method": "lora",                       // Training method: lora / qlora / full
  "dataset_path": "dataset/train.jsonl",  // Dataset path (relative or absolute)
  "output_dir": "./output/my_model_v1",   // Output directory (must be empty)

  // === LoRA/QLoRA only ===
  "lora_r": 8,                            // default 8. LoRA rank (higher = more parameters, better quality but slower)
  "lora_alpha": 16,                       // default 16. LoRA scaling (usually 1-2x lora_r)
  "lora_dropout": 0.05,                   // Dropout (guards against overfitting)
  "lora_target_modules": [               // Modules to train (null = use defaults)
    "q_proj", "k_proj", "v_proj", "o_proj",
    "gate_proj", "up_proj", "down_proj"
  ],

  // === Training hyperparameters ===
  "num_train_epochs": 3,                 // Number of epochs
  "per_device_train_batch_size": 1,      // Per-step batch size (drop to 1 when memory is tight)
  "gradient_accumulation_steps": 8,      // Gradient accumulation steps (effective batch = batch * accum)
  "learning_rate": 2e-4,                 // Learning rate (1e-4 to 3e-4 is typical for LoRA/QLoRA)
  "warmup_steps": 100,                   // Learning-rate warmup steps
  "max_seq_length": 2048,               // Maximum sequence length (longer inputs are truncated)

  // === Dataset field configuration (choose one) ===
  // Mode 1 (loss over the full sequence):
  "text_field": "text",
  // Mode 2 (completion-only loss, recommended for instruction tuning):
  "prompt_field": "prompt",
  "completion_field": "completion",

  // === Saving ===
  "logging_steps": 10,                   // Report loss every N steps
  "save_steps": 500,                     // Write a checkpoint every N steps
  "save_total_limit": 2,                 // Maximum number of checkpoints to keep
  "save_tokenizer": true,                // Whether to save the tokenizer

  // === Trainer selection ===
  "use_sft_trainer": true,               // Use the TRL SFTTrainer (recommended)
  "packing": false,                      // Whether to enable sequence packing
  "gradient_checkpointing": true,        // Gradient checkpointing (saves VRAM)

  // === DeepSpeed (optional) ===
  "use_deepspeed": false,
  "deepspeed_profile": "zero3_offload_cpu_cpu",  // Use a built-in profile
  // or
  "deepspeed_config": "./my_deepspeed.json",       // Use a custom config path
  "offload_folder": "./deepspeed_offload"          // ZeRO offload directory
}

8. DeepSpeed Offload Configuration

When GPU VRAM cannot hold the full model — typically with full-parameter training or LoRA on a large model — you can enable DeepSpeed ZeRO-3 offload to move part of the data to CPU RAM or NVMe disk.

Note: DeepSpeed lengthens training time significantly (CPU offload is 3-5x slower, disk offload 5-20x slower). Try QLoRA with a smaller batch size first, and enable DeepSpeed only when necessary.

The four built-in profiles

Profile name Optimizer offload Param offload Best suited for
zero3_offload_cpu_cpu CPU RAM CPU RAM Plenty of CPU RAM (>64GB); the most common choice
zero3_offload_cpu_cpu_tight CPU RAM CPU RAM Same devices as above with trimmed settings, for hosts where the standard cpu_cpu profile is too heavy
zero3_offload_cpu_disk CPU RAM NVMe Disk Limited CPU RAM but a fast NVMe drive
zero3_offload_disk_cpu NVMe Disk CPU RAM Special cases
zero3_offload_disk_disk NVMe Disk NVMe Disk Very low-memory environments; requires a fast NVMe drive

Example configuration with DeepSpeed enabled

{
  "model_name": "Qwen/Qwen3-14B",
  "method": "lora",
  "dataset_path": "dataset/train.jsonl",
  "output_dir": "./output/qwen3_14b_lora",
  "use_deepspeed": true,
  "deepspeed_profile": "zero3_offload_cpu_cpu",  // Use a built-in profile
  "offload_folder": "./deepspeed_offload",         // Overrides the profile's nvme path, if it has one
  "gradient_checkpointing": true,
  "lora_r": 16,
  "lora_alpha": 32,
  "num_train_epochs": 3
}
Special handling for DeepSpeed + LoRA: the default ZeRO-3 save_model behavior is incompatible with LoRA adapters (it can raise OOM or FileExists errors). The system already overrides save_model in CustomSFTTrainer and CustomTrainer, using GatheredParameters to safely gather the adapter parameters before saving, so this is handled automatically.

9. Post-Training Workflow

Automated post-processing: once training completes successfully, the system runs the following steps automatically — no manual action required:

Automatic GGUF conversion

  1. Training finishes and the model is saved to output_dir.
  2. Training resources are cleaned up (VRAM released).
  3. conversion_manager.convert_and_quantize() is called:
    • First the HF-format model is converted to GGUF F16.
    • Then it is quantized to Q4_K_M (smaller on disk, faster inference).
  4. The GGUF file is stored inside output_dir.
  5. The GGUF paths are not on /training/status — TrainingStatus has no gguf_path / gguf_quantization field, so they are filtered out of the response. Read them from the job log (/training/{job_id}/log, the finalize stage event) or from meta.json.

Automatic registration in the model registry

After training, the fine-tuned model is registered in models_registry.json under the finetuned type and can be queried through this API:

GET /config/models
// The response includes:
{
  "finetuned_models": [
    {
      "label": "my_model_v1",
      "output_dir": "./output/my_model_v1",
      "base_model": "Qwen/Qwen3-4B",
      "method": "lora",
      ...
    }
  ]
}

Running inference with a fine-tuned model

A trained model can be loaded directly through the Inference API by pointing model_path at the output_dir:

POST /inference/load_model
{
  "model_name": "my_model_v1",        // Registry label
  "model_path": "./output/my_model_v1", // Fine-tuning output directory
  "engine": "transformers",
  "quantization": "none"              // The adapter is already low precision; no extra quantization needed
}

Or use the automatically converted GGUF model (recommended for production):

POST /inference/load_model
{
  "model_name": "my_model_v1_gguf",
  "model_path": "./output/my_model_v1/my_model_v1-Q4_K_M.gguf",
  "engine": "llama_server",
  "n_gpu_layers": -1
}

10. Troubleshooting

❌ Error: Output directory already exists and contains files

Cause: output_dir still holds leftover files from a previous run.

Fix:

  • Empty or delete output_dir manually.
  • Or use a new directory name (for example add a version suffix: my_model_v2).
The system never clears the output directory for you, to avoid accidentally destroying earlier training results.

❌ CUDA Out of Memory (OOM) during training

Symptom: training crashes and /training/error_details reports is_oom=true.

Fixes (in order of preference):

  1. Call POST /training/force_cleanup_gpu to make sure VRAM is released.
  2. Switch to method: "qlora" (4-bit quantized base model).
  3. Lower per_device_train_batch_size to 1 and raise gradient_accumulation_steps.
  4. Lower max_seq_length (2048 → 1024 → 512).
  5. Enable DeepSpeed CPU offload: use_deepspeed: true, deepspeed_profile: "zero3_offload_cpu_cpu".

❌ Training Error: RuntimeError / CUBLAS_STATUS_ALLOC_FAILED

Cause: a PEFT device-placement problem in a multi-GPU environment.

Fix: the worker process already sets CUDA_VISIBLE_DEVICES=0 so that only GPU 0 is used. To use multiple GPUs, switch to DeepSpeed distributed training.

❌ Training finished but GGUF conversion failed

Cause: the llama.cpp conversion scripts are not installed, or the disk holding output_dir is out of space (GGUF conversion needs an extra 2-3x).

Fix:

  • Verify that the llama.cpp dependencies are installed.
  • Verify that the disk holding output_dir has enough free space (3-4x the original model size).
  • The HF-format model is still in output_dir and can be loaded with the Transformers engine.

❌ Loss does not converge, or stays at 0

Cause: the dataset format is wrong, or completion_only_loss leaves no trainable tokens.

Fix:

  • In two-field mode, make sure the completion field has enough text (it must not be empty).
  • If completions are very short (< 10 tokens), try the single-field text_field mode instead.
  • Make sure max_seq_length is not so small that completions get truncated away entirely.
  • Reduce learning_rate (for example 2e-4 → 1e-4).

❌ Redis connection failed: training history unavailable

Symptom: /training/status/{session_id}/history returns 404, or the logs show a Redis connection warning.

Explanation: Redis is optional, but there is no in-memory fallback for history. Without Redis, /training/status/{session_id}/history returns 200 with empty logs for a live session (404 for an unknown one). The durable record is events.jsonl — read it through GET /training/{job_id}/log, which works with or without Redis.

Fix: start the Redis service (redis-server) and set REDIS_URL, or REDIS_HOST/REDIS_PORT, in .env.

❌ DeepSpeed nvme offload path is not writable

Symptom: DeepSpeed training fails and the logs show errors related to the nvme path.

Fix:

  • Verify that the offload_folder directory exists and is writable (the system creates it, but the parent directory must be writable).
  • Verify that there is enough disk space (ZeRO-3 disk offload can need tens of GB).
  • Use an NVMe SSD rather than a traditional HDD — the speed difference is enormous.
